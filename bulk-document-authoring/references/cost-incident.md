# 成本事故：12.7 万字花掉 7224 万 token

2026 年 11 月 22 日，用多 Agent 生成一份 24.8 万字员工手册时实测。数据来自工作台的会话日志（`~/.dsh/sessions/**/session.v4.jsonl.zstd`），逐条累加 `assistant/message` 记录上的 `usage` 字段。

## 发生了什么

第一阶段：第 1～20 章，每章一个子 Agent，提示词要求"5,600～6,300 个汉字"。

| 指标 | 数值 |
|---|---|
| 子 Agent 数 | 27 个（中途重启过） |
| 模型调用次数 | 918 |
| 总 token | 72,249,380 |
| 输出 token | 1,591,072 |
| 缓存读取 token | 69,750,144 |
| 产出汉字 | 126,948 |

其中两个 Agent 单独看：

| 会话 | 模型调用 | 工具调用 | token |
|---|---|---|---|
| A | 97 | edit 49 次、bash 30 次、read 10 次、write 7 次 | 11,950,501 |
| B | 104 | 同样的模式 | 11,640,716 |

两者各自只产出约 6,300 个汉字。`bash` 调用是在数字数，`edit` 调用是 Agent 为凑字数逐节补写。

单次调用的平均上下文约 9 万～12 万 token——系统提示、工具定义、技能目录——每次调用都重发一遍。

第二阶段：第 21～34 章与附录，每个单元只 `write` 一次，不数字数、不回改。

| 指标 | 数值 |
|---|---|
| 子 Agent 数 | 19 个 |
| 模型调用次数 | 约 38 次 |
| 总 token | 772,507 |
| 输出 token | 183,313 |
| 产出汉字 | 121,000 |

## 得出的结论

1. **成本按模型调用次数计，不按字数计。** 第二阶段产出的字数几乎相同，token 只有前者的 1.07%。
2. **循环就是全部问题。** 每次 `edit` 都重发整个上下文。一句"把长度改对"可以让一章的成本放大 20～50 倍。
3. **长度校验必须放在 Agent 之外。** 脚本数字数是毫秒级；Agent 为了数字数重读自己的稿子，要多付一整份上下文。

## 连带浪费

- 子 Agent 上限是 8。一次 `parallel` 发出 14 个，实际启动 8 个、6 个静默失败，工作流仍然报告"已完成"。缺失单元是靠检查文件才发现的。
- 中断工作流后又重启"想快一点"：在途工作全部丢失，重启把已完成的也重新拉了一遍。
- 主编排会话花了 766 万 token，一部分是每个编排步骤都在重发几千 token 的工作流规格。
- 有一个附录 Agent 把内容直接回复出来、没有写文件，交付物缺了一节，直到列目录才发现。

## 由此提炼的规则

- 每个单元只调用一次工具：`write` 一次，然后一行确认。
- 写作 Agent 里禁用 `bash`/`edit`/`read`，校验交给拼装脚本。
- 子 Agent 上限为 8 时，每批不超过 6 个。
- 每批结束后验证文件；只重生成缺失的部分。
- 不要为了改吞吐中途重启。
- 用户问成本时，分阶段报 `输出 token`、`缓存读取 token`、`调用次数`。
