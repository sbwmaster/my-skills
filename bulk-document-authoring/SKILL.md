# 批量长文档写作

用低成本、可校验的方式产出长篇结构化 Markdown 文档。

真正的难点不是写文字，而是**成本模型**。Agent 里每一次模型调用都会重发它完整的固定上下文——系统提示、工具定义、技能目录，通常有几万 token。所以成本正比于**模型调用次数**，不正文的字数。一个 Agent 写完一章后开始数字数、改一段、再数、再改，就把一次生成变成了五十次，每次都按全量上下文计费。

一次真实事故：用"写→数→改"的循环产出 12.7 万个汉字，花了 **7224 万 token**；剩下 12 万个汉字改成每个单元只调用一次 `write`，只花了 **77 万 token**。内容质量没有差别，成本是 1%。

## 工作流程

1. **先固定交付形态。** 目标字数（以及"字"怎么算）、语言、分节粒度（章/节/篇）、单个文件还是多个文件、是否要封面、目录、附录、术语表、表单，标题最深到几级。
2. **选择生成方式**（见下表）。不要默认用 Agent。
3. **确定单元大小。** 一次 Agent 调用产出约 4,000～8,000 个汉字（英文约 2,000～3,000 词）比较合适。再长容易截断，再短则固定开销被放大的次数太多。用 `总字数 / 单元字数` 估算单元数——这是单元数，不是 Agent 数；一个 Agent 一次调用里可以写多个单元。
4. **先做一个试点单元。** 只生成第一章就停下来检查：结构、语气、具体程度、实际长度。这时候改提示词很便宜，全量跑完再改很贵。
5. **分批并发。** 同时运行的子 Agent 控制在 5～6 个以内。多数工具的子 Agent 上限是 8，超了会有部分启动失败，而失败通常**静默返回空值**，不会抛错。
6. **每批跑完必须验文件。** 逐个确认预期文件存在且大小合理。缺哪个单独重生成，不要整批重跑。
7. **用脚本拼装**，不要手工拼，也不要让 Agent 拼。脚本根据标题自动生成目录、拼接单元、输出统计。
8. **客观校验。** 数字数、检查章节编号是否连续、扫描占位符、检查标题是否重复。都通过之后再向用户汇报。

## 生成方式怎么选

| 方式 | 适用场景 | 相对成本 |
|---|---|---|
| 脚本 + 模板 | 内容是公式化的：表单、表格、清单、参数表、穷举列表 | 接近 0 |
| Agent 一次性生成单元 | 需要变化和判断的正文：制度、解释、案例、叙述 | 1 倍 |
| Agent 多步循环（写→数→改） | 几乎永远不用 | 50～100 倍 |
| 机械扩写已有文档 | 在用户给的骨架上填充 | 约 0.1 倍 |

大型文档通常是混合的：正文用一次性 Agent，附录（常见问题、术语表、表单清单、修订记录、联系渠道）用脚本或很短的一次性调用。

## 一次性成稿规则

给写作 Agent 最重要的一段约束：

```
## 硬性规则（违反会导致返工）
- 你的全部工作只有一次工具调用：调用一次 write 写文件。
- 禁止调用 bash/edit/read/glob/grep；禁止统计汉字个数；禁止回读或修改已写文件。
- write 的 content 参数里直接放完整正文，一次写全，写完立即结束。
- 长度按你的估计控制，宁可略短也不要回改。
```

如果 Agent 有可能自己推理"要不要检查长度"，在提示里把原因说透：数字数对脚本是毫秒级的事，对模型却意味着重新发送整个上下文；因此长度校验放在拼装脚本里，不放模型侧。

要预先接受两个后果：

- Agent 普遍会**写不到目标字数**。把目标定得比实际需要高一点，并接受 ±15% 的浮动。
- 某个单元偏短时，优先做**一次**定点扩写（"在 3.2 节后补约 800 字"）；一次不够就直接整章重生成，比继续循环便宜。
- Agent 有时会**直接在回复里给出内容、却没写文件**（它觉得不需要工具）。只以"文件是否存在"为准，永远不要把 Agent 的聊天回复当成交付物。

## 编排细节

- **规格不要反复放进对话。** 一长串章节规格如果写在编排参数里，每个编排步骤都会重发一次。把规格落到文件里、只传路径，或者接受一次性的开销。
- **先做幂等。** 启动前列出已存在的单元文件并跳过。被中断的工作流会在磁盘上留下已完成的部分，整体重跑等于重复劳动。
- **不要为了"提速"重启工作流。** 中断会丢掉在途的单元，重启又会把已完成的重新拉起。吞吐不够就调整批次大小，而不是重启。
- **区分三种失败：** 子 Agent 因上限没启动、启动了没写文件、写了但被截断。三者都用同一种方式发现——检查文件存在性与大小。
- **并行批可能超上限。** 上限是 8 时，一批 14 个会有 6 个静默失败。要验证每个单元，而不是相信工作流的返回值。

## 拼装

使用 `scripts/assemble_markdown.py`，约定目录结构：

```
<文档根目录>/
├── _front.md            # 封面、元信息表、前言、使用说明、版本历史
├── _chapters/chNN.md    # 每单元一个文件，首行是 "## 第 N 章 ..."
├── _appendix/appX.md    # 可选附录
└── <输出>.md            # 拼装结果
```

脚本会从 `##` 和 `###` 标题自动生成两级目录、用分隔线拼接各部分，并打印统计。拼完再跑 `scripts/check_document.py` 做结构校验。

几个让文档后续可用于检索（RAG）的约定：
- 全文只有一个一级标题（书名），放在封面文件里。
- 章用二级标题、节用三级标题，不跳级。
- 凡是可比较的内容都用表格：适用范围矩阵、审批权限、时限表、假期类型、报销标准。
- 封面写明文档编号、版本、生效日期、归口部门、版本历史；附录放常见问题、术语表、表单清单、修订记录、联系渠道。

## 校验清单

`check_document.py` 能机械检查其中大部分：

- [ ] 章节编号连续、不重复
- [ ] 没有占位符：`（略）`、`待补充`、`本章完`、`TODO`、`示例公司`、`Lorem`
- [ ] 没有重复的三级标题
- [ ] 标题层级一致（章二级、节三级）
- [ ] 字数达到目标，且按用户理解的口径统计
- [ ] 表格能正常渲染（每个表格都有 `|---|` 分隔行）
- [ ] 封面版本历史与目录都在

## 核算真实成本

如果运行环境保留了会话日志（DeepSeek Harness 在 `~/.dsh/sessions/**/session.v4.jsonl.zstd`，每次模型调用一条 JSONL 记录，带 `usage` 字段），用 `scripts/token_report.py` 汇总。缓存读取 token 通常占大头，它们按输入 token 的一小部分计费，所以总 token 数会高估实际费用。要对比同一任务的不同阶段，才能看出一次性成稿规则有没有生效。

用户问成本时，把"输出 token / 缓存读取 token / 模型调用次数"三者分开报——这比一个总数更能解释钱花在哪。

## 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 十来万字花掉几千万 token | 每单元 Agent 在写→数→改之间循环 | 每单元只 `write` 一次，长度交给拼装脚本校验 |
| 章节比目标短 30% | Agent 提前收尾，没有反馈回路 | 目标上调约 10%，接受 ±15%，或做一次定点扩写 |
| 部分单元缺失但工作流显示"已完成" | 超出子 Agent 上限，失败静默返回空值 | 每批不超过 6 个；每批后验文件 |
| 重启之后更慢 | 中断丢了在途工作，重启又重跑全部 | 不要中途重启；让启动幂等 |
| 单元文件里是确认语而不是正文 | Agent 只写了占位内容 | 检查文件大小，重新生成该单元 |
| 目录不正确 | 手工拼目录 | 拼装时从标题生成 |
| 成品超出目标 25% | 每个单元都超出 | 接受，或下次把单元调小；不要要求 Agent "修正长度" |
| 内容重复、全是套话 | 单元之间没有边界 | 给每个单元明确的"覆盖内容"和"不要写"清单 |
