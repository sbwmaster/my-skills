# 项目机械改动

机械改动的成本不在"写"，在**轮次 × 上下文**。每次模型调用都要重发完整历史，而每次工具调用的参数和结果都永久留在历史里。于是：改动越多 → 上下文越大 → 后续每一轮越贵，总成本随轮次近似平方增长。

一次实测：11 个文件、2,638 行、282 处注释翻译，用逐条 `edit` + 每文件校验跑了 **106 轮 / 949 万 token**；同样的产出用脚本或整文件写入只要 **10～25 轮 / 50～150 万 token**。按单次 `edit` 平均 3.4 万 token —— 而真正的产出只有 4 万字符。

完整数据见 `references/case-token-cost.md`。

## 一、先判定：这是不是机械改动

三个问句，全部为"是"才可以套本技能：

1. **能用一句话写出映射规则吗？**（"所有 `old_api` 改成 `new_api`"、"所有英文注释改成中文"、"每个文件加 SPDX 头"）
2. **规则的输入是可见的吗？** 不需要读业务逻辑、不需要判断"这里该不该改"。
3. **每一处的结果是确定的吗？** 换个人按同样规则做，得到同样的结果。

有一条是"否"，就不是机械改动：先把它拆成"机械部分 + 判断部分"，机械部分照本技能做，判断部分单独做。典型反例：重构函数、抽公共逻辑、修 bug、改行为、设计新接口——这些不要套。

## 二、七步流程

1. **写规则。** 一句话的映射 + 例外清单（哪些文件不碰、哪些字符串不改、哪些注释要保留）。写下来，不要留在脑子里。
2. **定不变量。** 明确"改完之后必须仍然成立的事实"：代码语义、字符串字面量、标识符、行尾、指令注释、配置解析结果。它同时就是第六步校验脚本的规格。
3. **建基线。** 先 `git commit`（或 `cp -r` 快照）。后面只跟基线对比一次，不靠记忆。
4. **只读一次。** 整文件 `read`，或 `grep` 定位后读区段。读过的内容不要回读——它已经在上下文里。
5. **批量改。** 按下面的表选方式。脚本替换优先，其次整文件 `write`，最后才是 `edit`。
6. **一次性校验。** 全部改完后跑一次 `verify_edit.py`，不要每改一个文件跑一次。
7. **提交并汇报。** 机械改动单独一个 commit；汇报只给文件数、处数、校验结果，不贴 diff。

## 三、选执行方式

| 改动形态 | 做法 | 典型轮次 |
|---|---|---|
| 有映射规则、输入可见：改名、固定串替换、加头、改 import、正则 codemod | 生成 `ops.json`，`scripts/apply_edits.py` 一次应用 | 2～4 |
| 仓库里已有工具能做：格式化、import 排序、lint 自动修 | 直接跑 `black` / `isort` / `ruff --fix` / `prettier` / `gofmt`，全仓一次 | 1～2 |
| 每处都要重新组织语言：注释本地化、docstring 重写、文档改写 | 每个文件一次 `write` 整文件重写；文件 > 500 行改用批量 `edit` | 1～2 / 文件 |
| 无法脚本化、也不适合整文件写 | 批量 `edit`，**每轮 8～12 个并行调用**，按文件分组 | 处数 / 10 + 2 |
| 逐处一个 `edit`、每文件一次校验、改完回读确认 | 不要用 | = 处数 |

**先算轮次预算**：需要写出的内容量 ÷ 单轮输出上限（通常 4k～8k token）= 物理下限。

| 任务 | 需要写出 | 物理下限 | 合理目标 |
|---|---|---|---|
| 2,600 行注释/docstring 翻译 | 约 2.5 万 token | 7～8 轮 | 10～25 轮 |
| 200 处固定字符串替换 | 约 2k token | 1 轮 | 2～3 轮 |
| 50 个文件加许可证头 | 约 3k token | 1 轮 | 2 轮 |
| 全仓跑一次 formatter | 0（工具做） | 1 轮 | 1～2 轮 |

实际轮次超过物理下限 3 倍，一定是方式选错了，不是任务太大。

## 四、脚本批量替换（最省的一种）

`scripts/apply_edits.py` 读一个 JSON 操作列表，一次把整批替换做完：

```json
[
  {"file": "src/a.py", "old": "旧文本", "new": "新文本"},
  {"file": "src/a.py", "old": "重复片段", "new": "替换片段", "count": "all"},
  {"file": "src/*.py", "old": "本应消失的写法", "count": 0},
  {"file": "src/a.py", "old": "^def (\\w+)\\(", "new": "def \\1(", "regex": true},
  {"file": "**/*.py", "prepend": "# SPDX-License-Identifier: MIT\n"}
]
```

- `count` 省略 = 1（必须恰好命中一次）；`"all"` = 至少一次、全部替换；`0` = 断言不存在（用来确认旧写法零残留）。
- 一个文件里任何一条不符合预期，整个文件都不写入（原子性），不会留半成品。
- 自动识别并保持文件原有的 LF/CRLF；混合行尾默认拒绝，避免悄悄统一风格。
- `.py` 写入前先 `compile`，语法错误不落盘。
- `prepend`/`append` 幂等：内容已存在就跳过，可以重复跑。
- 先 `--dry-run` 看命中规模，再实际执行。

生成 `ops.json` 要花一点输出 token，但它和改动量成正比、只出现一次；而每次 `edit` 都要重发一遍全部历史。几百处改动时，脚本是数量级的差异。

## 五、整文件 `write` 的边界

改动密度高的文件（注释翻译、docstring 重写、段落级改写）适合整文件重写：

1. `read` 原文一次；
2. 直接给出完整新文件内容，`write` 一次写入；
3. 没要求改的部分逐字复制；
4. 全部文件写完后统一校验。

两个限制：

- 单个文件超过约 500 行时，一次输出可能被截断。此时改用"每轮 10 个 `edit`"，**不要**把文件拆成两次 `write`（后一次会覆盖前一次）。
- `write` 覆盖整个文件，行尾风格要跟原文一致；不确定就用 `apply_edits.py`，它按行尾自适应。

## 六、批量 `edit` 的规则

不得不逐处修改时：

- 同一轮放 8～12 个 `edit`（并行工具调用）。一轮一个是最贵的模式。
- 不要每改完一个文件就 `bash` 跑校验——那也是一轮，而且在更大的上下文里跑。
- 不要改完 `read` 回读确认。交给校验脚本一次性确认。
- `old_string` 必须唯一。多行匹配经常因为空行带尾随空格而失败；拿不准就按单行替换，或改用脚本。
- 中文通常比英文短，不会撑破缩进；如果某行明显变长，说明加了原文没有的信息。

## 七、校验：证明"只改了该改的"

`scripts/verify_edit.py` 把不变量固化成六个档位，`--profile` 选一个：

| 档位 | 适用 | 强制成立的事实 |
|---|---|---|
| `comment` | 注释 / docstring / 文案本地化 | 去掉 docstring 的 AST 一致、docstring 数量一致、非 docstring 字符串一致、指令注释原样、行尾一致；行数变化只警告 |
| `message` | 日志 / 错误文案统一 | 结构一致（字符串内容折叠成占位符）、字符串个数一致、行尾一致 |
| `format` | 格式化 / import 重排 | 完整 AST 一致、非空白 token 序列一致、行尾一致 |
| `rename` | 批量重命名 | 基线按 `--rename 旧=新` 映射后与改后 AST 完全一致、字符串里的旧名一并映射 |
| `text` | 配置 / 文档 / 其它文本 | 能解析的格式（json/yaml/toml/ini/env）解析结果相等、行尾一致 |
| `syntax` | 其它改动的最低保障 | 仍能解析 / 编译 |

```bash
python3 scripts/verify_edit.py --profile comment 'src/**/*.py'
python3 scripts/verify_edit.py --profile rename --rename old=new 'src/**/*.py'
python3 scripts/verify_edit.py --profile text --base 01f8db3 'config/*.yaml'
python3 scripts/verify_edit.py --profile format --summary 'src/**/*.py'
```

- 基线默认 `HEAD`；`--base REF` 指定提交；`--base-dir DIR` 用快照目录。
- `--summary` 只打印失败项与统计，适合最后汇报。
- 默认严格。只有确实要改这些内容时才用 `--allow string,comments,docstrings,lines,eol`；要禁止 docstring 并行加 `--strict-lines`。
- 一个 diff 跑一次，不要按文件跑。

校验通过后跑一遍测试。测试失败先对比基线确认是不是原有失败，不要默认是本次改动引入的。

## 八、提交与汇报

- 机械改动单独一个 commit，别和功能改动混在一起：`git diff --stat` 要能一眼看出"只动了这些"。
- 提交前 `git status` 确认没有把不该提交的文件带进去（本地配置、密钥、`__pycache__`）。
- 汇报给三个数：改了哪些文件（数量）、多少处、校验结果。不要贴 diff，不要逐个文件复述。

## 九、委派给子 Agent（可选）

默认**不要**委派：主 Agent 直接做，省掉一层上下文复述。确实要并行时才拆，并且把成本约束写进指令，子 Agent 会忠实复刻你的做法：

```text
## 执行方式（按这个来，不要自由发挥）
- 每个文件先 read 一次，然后用 write 整体重写；文件超过 500 行时改成批量 edit。
- 需要 edit 时，同一轮并发 8～12 个调用，不要一次只发一个。
- 禁止：每改完一个文件就跑校验、改完回读、逐处 grep 确认。
- 全部改完只跑一次 verify_edit.py --profile <档位>。
- 汇报只给：文件数、改动处数、校验结果。
```

每个子 Agent 不超过 2 个文件、40 处改动；并行子 Agent 不超过 8 个（常见上限），超出会静默失败。子 Agent 的上下文也要花钱，拆得越碎越贵。

## 十、常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| token 是必要值的 10～30 倍 | 逐处 `edit` + 每文件校验，轮次被放大 | 改脚本替换或整文件 `write`；校验只做一次 |
| 单轮输出被截断，文件内容不全 | 一次写入超过输出上限 | 文件 > 500 行改用批量 `edit` |
| `edit` 报 old_string 未找到 | 多行匹配里带了尾随空格 / 特殊字符 | 单行替换，或走脚本 |
| 行尾从 CRLF 变成 LF | 按文本模式整读整写 | 校验档位会拦下；替换脚本用二进制读写 |
| 日志文案、prompt 被"顺手翻译" | 把字符串字面量当成了注释 | `comment` 档位会拦下 |
| `# type: ignore` 被删 | 整行注释被当成普通英文注释 | `comment` 档位会拦下 |
| `prepend` 把头插到了 shebang 前面 | 头必须让位给 shebang / coding 行 | 用 `old=<shebang>`、`new=<shebang>+头` 的替换 |
| 改名漏掉了字符串里的动态引用 | AST 看不见 `getattr(obj, "old")` | 替换后加 `{"count": 0}` 断言旧名零残留 |
| 格式化产生上万行无关 diff | 仓库没有 formatter 配置，风格与现状冲突 | 先只格式化本次要改的文件，或单独一次全仓格式化 |
| 测试挂了，以为是自己改坏的 | 仓库本来就有失败 | 先对比基线跑一次，确认失败集合没变 |
| 回读确认、反复 grep | 不信任自己的改动 | 交给校验脚本，人只看结果 |

## 十一、成本核算

如果运行环境保留 DSH 会话日志，用 `scripts/cost_report.py` 汇总，重点看三个数：

```bash
python3 scripts/cost_report.py ~/.dsh/sessions/<项目>/<会话>/
```

它输出轮次、工具调用分布、缓存读取、输出量、平均每轮。判断标准：

- 平均每轮 > 5 万 token → 轮次太碎；
- 每次工具调用 > 2 万 token → 在逐处改，没有批量；
- 实际轮次 > 物理下限 3 倍 → 执行方式选错了。

缓存读取按输入价格的一小部分计费，所以总 token 会高估实际费用，但它仍然是最好的过程指标。
